# yue2-karaoke-align

An independent feasibility spike: **can we get word/phrase-level lyric
highlighting (karaoke) for songs generated by the sibling project**
[`maqamrock-yue2-lora-finetuning`](../maqamrock-yue2-lora-finetuning)?

Suno's studio editor does this natively. This repo asks whether *our* workflow
can, and what it would actually cost. It is **docs-first**: a phased plan, an
honest assessment, and small runnable CPU checks. Track A (post-hoc forced
alignment) now has a working pipeline; Track B (native extraction) is still a
spike.

## Verdict (short)

- **Post-hoc forced alignment works on our corpus — at word level.** A
  *forced* aligner with the known lyrics (not WhisperX/ASR) survives vocal
  separation on real YuE2 renders: 8/8 songs, 100% monotone, no words in the
  silent intro. The production model is pinned, and
  [docs/A1-RUNBOOK.md](docs/A1-RUNBOOK.md) turns a run directory into word
  timings + VTT/SRT + a karaoke player. Limits: a speech-trained model on sung
  audio, one aligner family, and no gold-anchor accuracy number yet.
  See [docs/ROUTE-A.md](docs/ROUTE-A.md).
- **The native route** (read the alignment out of the generation itself) is
  **doable as a demo, a headache as a production feature**: ~3–5 days to a
  base-model demo, ~1–2 weeks with real uncertainty to make it faithful to our
  own LoRA renders. See [docs/FEASIBILITY.md](docs/FEASIBILITY.md).
- **The browser player is trivial** (~half a day) and is independent of how the
  timings are produced. It exists: `scripts/a0_player.py`, driven by the A1
  pipeline.

If you just want the best model: [docs/BENCH-PLAN.md](docs/BENCH-PLAN.md)
— metrics, shortlist (incl. Quran-trained and phoneme-level Arabic models),
and the Colab procedure. Licensing is out of scope (personal use).

## Quick start

Environment: a Python venv with `torch`, `torchaudio`, `transformers`, `demucs`
and `soundfile`; see [docs/A0-RUNBOOK.md](docs/A0-RUNBOOK.md#prerequisites-once).
No GPU is required.

The pipeline accepts two input shapes — pick the one that matches what you have:

```bash
# 1. Flat pair: <name>.mp3/.wav + <name>.txt (same basename)
.venv/bin/python scripts/a1_align_run.py --data-dir path/to/song --auto-songs

# 2. YuE2 run directory: <name>_<seed>.wav + prompts/<name>_lyrics.txt
.venv/bin/python scripts/a1_align_run.py --run-dir path/to/out/<run>

# Always cheap to check first: lists the pairing, no model load, no writes
.venv/bin/python scripts/a1_align_run.py --data-dir path/to/song --auto-songs --dry-run
```

For mismatched names, FLAC, or an explicit per-song list, use `--songs`
(see the [input contract](docs/A1-RUNBOOK.md#input-the-minimum-shape)).

Each run writes `results/a1/<label>/`:

| file | contents |
|---|---|
| `<song>.words.json` | **word-level** timings + QA + lyric-line indices (source of truth) |
| `<song>.vtt` / `<song>.srt` | **line-level** subtitles, one cue per lyric line |
| `<song>.player.html` | self-contained karaoke page driven by the word timings |
| `summary.json`, `A1-REPORT.md`, `index.html` | machine summary, QA table, links |

Word-level timing is in the JSON and the player; `.srt`/`.vtt` are line-level
(what a normal subtitle player can display). The player links its audio by
relative path, so it travels with the source file.

## Why this might work at all

YuE2's AR stream is conditioned on the diacritized lyric tokens and emits a
25 Hz semantic token stream — the only ~375 bit/s channel from text to audio.
The model renders `سِ` differently from `سٍ`, so a per-syllable lyric→frame
correspondence *causally exists* in the generation. It is never written to any
output file (the runtime exports no attention), so it has to be **tapped, not
found**.

## Relationship to the sibling project

Standalone. This repo **consumes** the sibling's rendered audio + prompt lyrics
(read-only) and **never modifies it** — no training, datasets, GCS, or
`INFERENCE/` scripts. See [docs/PARENT-CONTEXT.md](docs/PARENT-CONTEXT.md).

## Status (2026-10-21)

**Track A is validated and has a batch pipeline.** A0a passed on a Suno proxy;
B2 then ran 6 aligners × **8 real YuE2 renders**, which satisfies the A0b gate.
That run eliminated MMS-1b (words in the silent intro, 8/8), the Egyptian model
(collapsed to 1 word/song) and the phoneme model (energy tracking inverted).
The production aligner is the pinned base mirror
`akbargherbal/wav2vec2-large-xlsr-53-arabic`; the Quran fine-tune tied within
one CTC frame and is kept as a spare.

`scripts/a1_align_run.py` now takes a run directory (or a flat staged dir) and
writes word JSON, line-level VTT/SRT, a karaoke player, a QA report and an
index page. See [docs/A1-RUNBOOK.md](docs/A1-RUNBOOK.md). It has been run on a
**real 4-song YuE2 run directory**: 4/4 songs, 570 words, 0 silent-intro
violations (`results/a1/yue2-real/`). A single-song **flat two-file** run
(`song.mp3` + `song.txt`) also passed at 125/125 words and 24 line cues, with
the silent-intro check ok. A Suno smoke run reproduced A0a's first word at
**21.481 s** (A0a: 21.48 s). Run-dir outputs are keyed by the WAV stem, so
multiple seeds of one lyric do not collide.

**Not done:** the base/Quran model choice is still a cost tie rather than a
gold-anchor accuracy decision, and **Track B (native extraction) has not
started** — Phase 0 (the YuE2 tokenizer check) is still unrun.
